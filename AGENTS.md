# AGENTS.md — rules for every AI agent working on this repository

`CLAUDE.md` is a symlink to this file. Edit only `AGENTS.md`.
The full description of the workflow lives in `docs/workflow.md`; read it before changing anything in `.claude/`.

## Project
- `videolore` — a Rust project (edition 2024, MSRV 1.100, always the latest stable Rust). Version source of truth: `Cargo.toml` (`version`).
- License: GPL-3.0 (`LICENSE`). Author and owner: Andrea Lorenzani.

## Agents and the documents they own
| Agent | Color | Private notes (AI-only, owner only) | Human-readable doc |
|---|---|---|---|
| `product-manager` | blue, haiku | `ai-docs/business.md` | `docs/business*.md` |
| `architect` | green, haiku | `ai-docs/architecture.md` | `docs/architecture*.md` |
| `principal-engineer` | red, sonnet or opus (rule 13) | `ai-docs/code.md` | `docs/code*.md` + the code in `src/`, `tests/`, `Cargo.toml` (except `version`), `.github/workflows/`, `github_page/` (rule 4e) |
| `documenter` | yellow, haiku | `ai-docs/notes.md` | any `docs/*.md` (no owner guardrail), `README.md`, `docs/changelog.md`, `docs/roadmap.md`, `docs/workflow*.md`, the version (via `scripts/version.sh`); never `LICENSE` text, never another agent's `ai-docs/` |
| `analyst` | purple, haiku | none (writes nothing) | none; **read-only** (`Read`, `Glob`, `Grep`), used only by `/analysis` |

## Rules (MUST)
1. **The `documenter` runs at the end of every part of a development** (every feature, fix, refactor, dependency change or workflow change): after the product-manager, after the architect, after the principal-engineer. Each call only updates documentation (changelog, roadmap, README, `docs/`, notes index). A development is not finished until the documenter has run after its last change.
2. **Ownership**: a file in `ai-docs/` is written only by its owner agent; other agents may read it, never edit it. Human docs in `docs/` and `README.md` may be written by their owner or by the `documenter`, which has no ownership guardrail for them and reports what it changed.
3. `ai-docs/*.md` are notes by AI for AI, and they are **short**. The main file of each owner is an **index**: one line per paragraph (heading) of every human doc it manages, with its line range and length, e.g. `- docs/architecture-ffmpeg.md § Subtitle rendering — L40-62 (23 lines)`. The agent finds a paragraph with `grep -n` on the index and reads only that line range (`sed -n 'A,Bp'`). The index is refreshed by the owner whenever it changes a managed doc (`grep -n '^#' <doc>` gives the headings).
3b. **Sub-documents of `ai-docs/`**: an owner may put much more AI-oriented detail (ADRs, measurements, module maps, decision logs) in `ai-docs/<area>-<topic>.md`. Each one is indexed in the owner's main `ai-docs` file in the same format, and is read only when a task needs it. Sub-documents have the same owner as their index.
3c. **Hand-off between agents**: work passes through files, not through the command. An agent writes its plan, decisions and results into its own notes and human docs; the next agent reads them by path. The command passes only file paths, the user's answers and short counts (coverage, implemented REQ ids). An agent's return to the command is at most: `[SEVERE]` questions for the user (with options), the list of files it changed, and short `## Future work` bullets.
3d. **Human docs**: `docs/*.md` are for humans: brief, but with every detail a human cares about. An owner may split `docs/<area>.md` into `docs/<area>-<topic>.md` (e.g. `docs/business-ui.md`) when it passes ~150 lines or mixes distinct topics; `docs/<area>.md` stays the index linking every sub-document. Sub-documents have the same owner and rules as their index.
4. **Versioning — every development bumps the version, everywhere.** A development (feature, fix, refactor, dependency or workflow change) gets one new version. If the user names the version, use it; otherwise increment the **last number by one** (0.1.0 → 0.1.1 → 0.1.2); after a `/release` the version moves to the next **major** (0.4.1 released → 1.0.0, 2.0.0, …). The command decides the target version at the start and passes it to every call; the documenter applies it on its first call, and later calls of the same development leave it unchanged. The version is changed **only** with `scripts/version.sh set X.Y.Z`, which updates every location (`Cargo.toml`, `Cargo.lock`, README version badge) and verifies them; `scripts/version.sh check` must pass before every commit (CI enforces it). A new place that shows the version must be added to that script.
4b. **Changelog**: `docs/changelog.md` lists the changes since the last release in reverse chronological order (newest first); each entry header is `## <version> — <YYYY-MM-DD HH:MM +zone>` (from `date '+%Y-%m-%d %H:%M %z'`). One entry per development: the documenter creates it on the first call and adds bullets on the later ones.
4c. **Releases** (`/release` only): the **current** version is released. Order: (2) **consolidation** before the gate and the snapshot — `documenter` (cleans and compacts `docs/`, cleans the README `Known limitations` and hands them to the Product Manager, creates the temporary `github_page/after release.md`), `product-manager` (prioritised `docs/roadmap.md` and `docs/roadmap_tasks.md`, cleans its docs), `principal-engineer` on `opus` (optimises code, tests and libraries, `docs/code-index.md`, `docs/code-architecture.md` with mermaid diagrams, cleans its docs), `architect` (verifies and stores the module architecture, cleans its docs); each appends its section to `github_page/after release.md`; (3) the Principal Engineer's VERIFY gate, the Documenter's release summary, `scripts/collect-release.sh` creates `releases/<version> - <name>/` with a copy of all docs unchanged (`README.md`, `docs/`, `ai-docs/`, so the architectural plans too), `sources.zip` and `RELEASE_NOTES.md` (taken from the changelog); (4) the plans `ai-docs/architecture-plan-*.md` are removed from `ai-docs/` (they live in the snapshot) and the changelog is cleaned; (5) commit, tag `v<version>`, push; (6) the version moves to the next major (`scripts/version.sh set`), the Documenter writes a **new README poem**, the Principal Engineer (`opus`) regenerates `github_page/` from `github_page/after release.md` and deletes that file, commit, push. **Files under `releases/` are never modified by anyone** (denied in `.claude/settings.json`, checked by `scripts/release-guard.sh` in CI); only Andrea deletes old snapshots, manually. `github_page/after release.md` is git-ignored (never committed, never in `sources.zip`).
4d. **Roadmap**: `docs/roadmap.md` (kept by the Documenter) lists the known limitations and improvements to do in future versions. Every agent returns a `## Future work` section with anything important for the future; the command passes these items (and the features a plan postpones from a request) to the Documenter, who keeps the roadmap current. On `/release` the Product Manager rewrites it as a prioritised list and writes `docs/roadmap_tasks.md` (the roadmap split into versions and batches, in the suggested order).
4e. **Project page** (`github_page/`, owned by the `principal-engineer`, regenerated by `/release` in step 6 and whenever the user asks): **every time it is regenerated** it points to the **last release** (`v<version>`: the version shown, the release link and the links to that release's artefacts, with names taken from the release, never invented) and has, **just after the project name**, a "Download" link to a Downloads section that lists the different artefacts (installers and executables per platform, editor and player). No reference to AI, agents or the workflow.
4f. **Splash files**: `assets/splash/splash.gif` (editor) and `assets/splash/splash-player.gif` (player) have fixed names and are **never copied per version**; the texts `assets/splash/summary.txt` and `summary-player.txt` (heading and at most five lines) are rewritten in place for each version that changes something users see.
5. **README**: it is for the users of the software. It must contain **no reference to AI, agents, commands or this workflow** (`ai-docs/`, `docs/workflow*.md`, `AGENTS.md`, `.claude/` are never mentioned). "Latest changes" lists **only the last 3 versions** with user-facing changes, by **version, never date** (`- **0.1.1** — ...`), with a link to the changelog and the release notes for older ones. **Poem**: the 10-verse poem at the end of `README.md` celebrates what Andrea Lorenzani has done for this project. It is replaced by a new one **only by `/release`, when the next major version is opened** (step 6, the Documenter's POEM mode); every other change to `README.md` keeps the poem as it is. Verses 1-9 end with a backslash `\` so GitHub renders one verse per line; verse 10 has none.
6. **Workflow changes** go through `/change-workflow` only, and `docs/workflow.md` must be updated with them.
6b. **The clone stays complete**: `/clone-workflow` is the skill `.claude/skills/clone-workflow/` (manifest, generic templates, scripts), copied with the project. Every workflow change updates it as described in `/change-workflow`, and `.claude/skills/clone-workflow/check.sh` must pass: every workflow file is listed, templates are reviewed after their file changes, and no project-specific word reaches a copied file.
7. **Tests are run only by the `principal-engineer`, after coding.** The quality suite is: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `scripts/coverage.sh --fail-under 85`, `scripts/feature-coverage.sh`. The Principal Engineer runs it **once, at the end of all the code of the development** (never after each step or each requirement while coding: during coding it writes tests together with the code and does not run the suite, except a single targeted `cargo test <name>` when it must understand one failure); if anything fails it fixes the **code** (never weakens or deletes a test to get green) and reruns the whole suite, until it passes. It then reports the results, the **line coverage** (one decimal) and the **feature coverage** (`implemented REQs with tests / implemented REQs`). No other agent, and no command orchestrator, runs tests, builds or coverage: they use the Principal Engineer's report. CI on GitHub runs the suite again independently.
7b. **Coverage**: line coverage **at least 85%** (`scripts/coverage.sh --fail-under 85`, `src/main.rs` excluded: it only wires `src/lib.rs`), and **feature coverage 100%**: every requirement marked `REQ-NNN (implemented)` in `docs/business*.md` has at least one test annotated `// covers: REQ-NNN` (`scripts/feature-coverage.sh`). The README coverage badge shows the value reported by the Principal Engineer with one decimal (e.g. `86.2%`), written by the documenter with `scripts/coverage.sh --badge <value>` (no test run).
8. Never invent facts in docs; mark assumptions as assumptions.
9. **Commits**: every development ends with a git commit. The message is one human-readable line (e.g. `Add prebuilt executables for Linux, macOS and Windows`), with no prefixes like `feat:`, no body and no mention of agents or AI in that line. The only other line allowed is the `Co-Authored-By:` trailer naming the model that did the work (after a blank line, as git requires). Push only when the user asks.
10. **Licence notice**: `LICENSE` holds the unmodified GPL-3.0 text. The copyright holder (Andrea Lorenzani) appears in the README licence section and in a header at the top of every Rust source file: `// SPDX-License-Identifier: GPL-3.0-only` and `// Copyright (C) <year> Andrea Lorenzani`.
11. **CI**: `.github/workflows/build.yml` checks fmt/clippy/test, coverage ≥85%, feature coverage 100%, version consistency and frozen release docs, then builds release executables (Linux, macOS, Windows) on every push to `main`; pushing a `v*` tag creates the GitHub release with the executables and the release log. Keep it green.
12. **Token economy**: agents read only what their task needs: the `ai-docs` index first, then the paragraphs they grep for. Every development the Documenter runs `scripts/docs-check.sh` (links, sub-document indexes, forbidden AI/agent terms, changelog headers, README latest changes and poem), which covers all of `docs/` mechanically, and fixes what it reports; it reads in full only the files the development changed (`git diff --name-only`) and the indexes they belong to. On `/release` (step 2) the Documenter reads and compacts every `docs/` file (not `ai-docs/`), and each agent cleans and compacts what it owns (its `ai-docs/` and its human docs): they remove only useless data (repeated sentences, stale process notes, finished plans, empty filler), make related data contiguous and keep every fact and every exact paragraph that a grep may need. Notes in `ai-docs/` are compacted by their owner only, never by another agent.
13b. **Replace without reading**: to change a requirement, an ADR or a version/number/word in a doc, an agent that knows the new text uses `scripts/doc-replace.sh` (`req REQ-NNN <new line>`, `adr ADR-NNN <new line> [file]`, `line <file> <ID> <new line>`, `text [--all] <old> <new> <file>...`) and **never reads the old paragraph or line first**; the script prints only the file and line range. The project version stays with `scripts/version.sh set`. If the line count changed (`+N lines`), the owner refreshes its `ai-docs` index with `scripts/doc-index.sh`; if it did not, the index is still valid.
13. **Models**: `product-manager`, `architect` and `documenter` always run on `haiku`. The `principal-engineer` runs on `opus` when the session's selected model is Opus, otherwise on `sonnet` (default). The agent files fix `haiku`/`sonnet`; the commands (`/add-feature`, `/release`) pass `model: opus` in the Agent call for the Principal Engineer when the selected model is Opus. The `principal-engineer` also runs on `opus` **always** in `/release` step 2 (consolidation) and in the page regeneration of step 6, whatever the session model is. The `analyst` always runs on `haiku`.

## Commands
- `/add-feature <description>` — feature pipeline: product-manager → architect → principal-engineer, the documenter after each part; the command only relays user questions and file paths.
- `/change-workflow <change>` — change agents, commands, rules, skills, guardrails.
- `/clone-workflow <directory>` — export this workflow to another directory (skill `clone-workflow`).
- `/analysis <question>` — ask a question about the project: the read-only `analyst` (haiku, tools `Read`, `Glob`, `Grep` only) reads all the documents and the code and answers; it can write nothing and the command changes nothing.
- `/release [name]` — release the current version: consolidation by all agents (the Principal Engineer on `opus` also optimises code, tests and libraries and writes the code index and the mermaid architecture) → VERIFY gate → `releases/<version> - <name>/` (docs incl. the architectural plans, sources zip, release notes) → plans archived and changelog cleaned → commit, tag `v<version>`, push → next major version with a new README poem and the project page regenerated for the released version (download link after the project name) → push.

## Scripts (`scripts/`)
`version.sh` (get/next-patch/next-major/set/check), `doc-replace.sh` (replace a requirement, an ADR or a literal text without reading it), `docs-check.sh` (mechanical docs consistency, Documenter), `coverage.sh`, `feature-coverage.sh`, `collect-release.sh` (release snapshot), `release-guard.sh`, `test-annotations.sh` (CI test failures as annotations), `notices.sh`, `icons.sh`, `fetch-ffmpeg.sh`, `package.sh` (installers).
