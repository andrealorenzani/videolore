# ai-notes: ADRs of 2.2.0 (owner: architect; PLAN 2026-11-21, REFINE 2026-11-21 after Q-1; index in ai-docs/architecture.md; plan in ai-docs/architecture-plan-2.2.0.md)

Status: BUILT 2026-11-22 (not released). REQ-315 and REQ-177 are measured and NOT MET (see the plan, section 14). Earlier status: PLAN, Q-1 answered (route D, Andrea 2026-11-21). Each ADR: context, choice, alternatives, reason.

ADR-214 (2.2.0 BUILT, route D, D63) LUT preview: the `.cube` route stays; the preparation is in the background with progress and an unprocessed picture meanwhile (REQ-312). Context: 2.1.0 gives the bundled ffmpeg 9.0.2 a `.cube` Work copy written as text (6 decimals); lut3d parses it on every start: 256 points 12.4 to 13.0 s, 144 points 2.26 s (measured, development machine, Intel Iris Plus G7). Andrea's answer: keep the route, no colour or graph change, show progress; the start time is not gated (about 12 s kept). Choice (D): the 2.1.0 route unchanged (`lut-<hash16>.cube`, `lut3d=...:interp=tetrahedral` on `format=gbrp`, same colours, same golden argv for LUT projects); the work of a LUT choice is a background preparation in the existing store (`lut/store.rs`: reading the file with progress, the streamed parse, the Work copy written once with progress; the states Loading, Ready, Failed of ADR-205 are extended by a phase and a percentage); the UI thread and the preview graph builder never parse or write (they read the store's state with `peek`); while the LUT is not Ready the preview graph is built without the LUT row, so the picture is the unprocessed one (no new LUT in the meantime); the preview restarts with the LUT when the copy is Ready and shows "Preparing LUT" with a percentage until the first graded frame arrives; a newer choice replaces the preparation (generation token and Load drop, as ADR-205; a partial copy is removed). Export waits for Ready in its own worker and shows the same status. Measured record (spike S0a, architect, scratch, 2026-11-21, kept as history): `lut3d` reads `.m3d` by extension, and the 9.0.2 reader is TEXT, not binary: header `in <n^3>` (entry count), `out <max+1>`, `values 0 1 2` (required; without it the read ends with "Unexpected EOF"), then one `r g b` line per entry, red outermost and blue fastest. 256-point starts: `.cube` 12.4 to 13.0 s; `.m3d` float 6-decimal 5.1 s; `.m3d` integer values 0..65535 with out 65536 (293 MB) 3.4 to 3.6 s; 144-point `.cube` 2.26 s. Integer `.m3d` vs 9-decimal `.cube` on a non-linear 144-point test LUT: at most one 8-bit level on 153 of 196608 output bytes. HALD binary image (`haldclut`, raw rgb48le 4096 x 4096 for 256 points): 0.36 s total, output within one 16-bit unit of lut3d on random frames; trilinear interpolation, 16-bit path needed in the 8-bit `gbrp` graph, planar path unverified. Alternatives rejected by Andrea's choice: A (`.m3d` integer, 3.4 to 3.6 s, one graph change of the table text), B (`.m3d` float, 5.1 s), C (binary HALD, 0.36 s, interpolation and pipeline change). Rejected in all cases: a smaller preview table (colours must be exact), an 8-bit HALD (1/255 quantisation), `.dat` (text in the 9.0.2 reader too). Consequences: no new file format, no golden change for LUT projects, the Work copy stays about 450 MB per 256-point LUT (2.1.0 size, no growth); the "Preparing LUT" status and the fallback are the new behaviour; the measured start time is recorded as a fact, not a gate. Risk: the first graded frame of a 256-point LUT comes after about 12 s, during which the picture is unprocessed; this is the accepted product behaviour (REQ-312 with D63).

ADR-215 (2.2.0 BUILT: whole-video copies) whole-video effects without a stored change (REQ-083, REQ-147, REQ-148, REQ-200..202, REQ-303, REQ-076). Context: since format 9 (ADR-122, ADR-125) every effect is stored per clip; the whole-video action (double-click) writes one copy per clip (`whole_edit`, `Target::WholeVideo`). What remains of the whole video is UI and command code: the whole-video popup of Scale and Move (`FrameTarget::Whole` for keyframes, `whole_ref` = first clip with keys, `SelectCopy`), the whole-video mark (`app/applied.rs` field `whole`, `ui/applied_effects.rs` mark), the new-clip offer (`app/offer.rs`, `ApplyWholeToNew`, status item with a button), dashed handles (`ui/frame_handles.rs`), the popup title "— whole video" for Scale and Move (kept for Change aspect only). Choice: remove those routes; keep the double-click copy routine (renamed `copy_to_clips` in the plan); a copy is an ordinary clip effect in every popup, handle and row. Storage: no field added, none removed; Change aspect stays `Timeline.frame_aspect`. The format is bumped to 13 for the order and the text maximum (ADR-222, ADR-221 superseded); the whole-video change itself adds nothing to the file. Alternatives: a stored whole-video flag (rejected: a second source of truth that the copies would have to keep in step); keep the popup hidden (rejected: dead code, and the widget mark would stay inferred). Reason: Andrea's answer of 2026-11-21 (REFINE: Fade IN/OUT stays on the first start and last end as copies; the whole-video popup and mark are removed). Consequence: 2.1.0 projects open unchanged (no data differs).

ADR-216 (2.2.0 BUILT: rows cache by serial) Applied effects rows are cached (REQ-313). Context: `app/applied.rs` builds the rows of the selected clip (or the clip under the playhead) on every frame, so the widget rebuilds them 60 times a second. Choice: `AppState` keeps the last rows with a key (clip id, a revision number of the order and effects, the selection rule); a command that changes the clip set, an effect, a LUT, a text, a picture item, a subtitle line or the order increments the revision (one place: the dispatch of commands that edit the timeline or the order); the widget reads the cached rows; a `cfg(test)` build counter counts row builds for the acceptance test. Alternatives: hash the clip each frame (costs the same as the build for long clips); memoise per clip without a revision (stale rows after undo). Reason: cheap and exact; undo and redo change the timeline, so they bump the revision too.

ADR-217 (2.2.0 BUILT: measured about 2 ms a frame, target met, no change) blurred fill in playback (REQ-314). Context: the blurred background is in the graph as `scale` to one eighth, `boxblur`, `scale` back (render/graph.rs, frame.rs BLUR_DIVISOR 8). Measured proxy (architect, ffmpeg 9.0.2, `testsrc2`, 300 frames, plain scale and pad versus the same plus the blur chain, no decoding): 1080p plus 3.2 ms per frame, 4K plus 1.8 ms per frame (the 4K plain chain itself takes 7 ms per frame). Choice: no change until the PE measures the real preview graph (S0b, app log, 1080p and 4K, 300 frames, median and 95th percentile). If the step is above the budget (one frame time at 4K, assumption), the candidate changes are, in order: (1) remove the full-size background scale (overlay the blur at the picture's size with the same geometry, if the result is identical); (2) a cheaper resample flag of the same filter (only if the output is unchanged within 2%); (3) a lower-resolution blur (changes the picture: a product decision, asked to Andrea, Future work). Rejected: a preview-only blur (breaks REQ-314 c, preview equals export) and a blur cache per frame (the video under the blur changes every frame).

ADR-218 (2.2.0 BUILT, lever (a) only: 8.7% gain against 20%, NOT MET; levers (b) and (c) not taken) Faster export on integrated graphics (REQ-315). Context: the output check (outcheck.rs, REQ-063) runs a full strict decode of the hardware file (step 2) and three one-second renders of the normal graph with psnr (REQ-206), after the hardware encode; on the Iris Plus G7 the total ranged from 14% quicker to 41% slower than Best quality (2.0.4). Choice: keep every check and the three samples (10, 50, 90%); first measure the phases on the Iris (S0c: export log with phase times, not in the output, 3 runs each for Best and Faster). Levers, in order: (a) run the full strict decode and the sample renders concurrently in the scheduler (within the process cap of ADR-015/029, never more than the cap); (b) skip the separate metadata pass if its result is already read by the strict decode (only if the same fault tests stay); (c) decode the hardware file with the hardware decoder for the strict pass (changes what the decode checks; only with a note in the docs and a test that a broken file is still caught). Rejected: fewer samples or a shorter range (REQ-063: every fault caught), no check on integrated graphics (REQ-063 applies to every machine). Reason: the check is the only proof that the quick file is right; its cost is what can be cut without losing a test.

ADR-219 (2.2.0 BUILT) picture limit 16 megapixels (REQ-316, amends REQ-287). Context: `picture.rs` reads only the PNG header (width and height) already (ADR-192); no decoded copy exists before the export. Choice: one constant `MAX_PICTURE_PIXELS: u64 = 16_000_000` in picture.rs; checked where the header is read: on Add picture (refusal, status message, nothing added), and when a project's picture is loaded for preview or export (missing-picture rule of REQ-287: the export stops with its message, the project still opens). No count limit, no file size limit, no copy in the project (Andrea 2026-11-21). Alternatives: a limit on decoded bytes (rejected: the header is enough and decoding happens later with its own caps, ADR-133). Reason: a single, testable rule.

ADR-220 (2.2.0 BUILT, NOT MET: 10 of 23 words (43%); FROZEN = None, old path is the default) speech-region timing for reused subtitles (REQ-177, amended 2.2.0). Context: 2.0.3 measured DTW (every word 0.43 to 0.75 s late), a one-sided energy-onset snap (7 of 23 matched words within 0.3 s), and a speech-region prototype (21 to 22 of 23 for 4 of 120 settings, all on the one synthetic clip with 0.15 s pauses; 12 of 23 for the rest). The onset snap code was removed in 2.0.3, so REQ-177's "after the onset snap" means the region-edge snap defined here (TECHNICAL, recorded). Choice: a pure module `src/speech_regions.rs` (new): 10 ms RMS frames in dB of the 16 kHz mono samples that the recogniser already has (no second decode); noise floor = 10th percentile of the clip's frames (no tuned value); speech frame when dB >= floor + T; gaps shorter than G are bridged; regions shorter than 0.10 s dropped; the words of each cue (as today, in order, never reusing an earlier cue's words) are placed over the regions in its window [cue start - 1 s, cue end + 1 s] by a small dynamic programme: each region takes k words, cost = |region length - predicted length| with a predicted length of max(0.1 s, characters / R) per word, plus a penalty lambda per skipped word; a matched word's recognised time picks the region edge when it lies in the region. Parameters: T, G, R, lambda; the grid is declared here before any second clip is seen: T in {9, 12, 15} dB, G in {0.12, 0.20, 0.30} s, R in {8, 10, 12} characters per second, lambda in {0.5, 1, 2} s (81 settings, one order). Selection (on the reference clip only): the setting with the highest count of matched words within 0.3 s; ties to the first in the order T, G, R, lambda ascending; a setting below 75% matched-within-0.3 s is not eligible. Frozen: no setting changes after the second clip is seen. Check: one run on the second clip (about 30 s, real speech, transcript by Andrea, committed with a sha-256 check as ADR-166); pass: at least 90% of matched words within 0.3 s on that clip with the frozen setting; fail: REQ-177 stays planned, the result is reported, no re-tune on either clip. Alternatives: DTW (measured late), a fuzzy text match (rejected by D56), a larger speech model (not planned, D54), an energy snap per word (7 of 23). Reason: it is the method Andrea chose; the grid and the rule are fixed in advance to limit overfitting to one clip. Risk: continuous speech has long regions (the prototype's reason for failing), so the check may fail; the plan says so.

ADR-221 (2.2.0 PLAN; SUPERSEDED by ADR-222: format 13) project format stays 12 (no bump). Context: every 2.2.0 item is either a code path (LUT preparation, rows cache, picture limit, speech regions, blur, Faster) or a removal of UI routes over fields that already exist (whole-video copies, ADR-215). Choice: SCHEMA_VERSION stays 12; no field added; no new Work-folder file format; the golden fixtures of formats 4, 5 and 12 and the LUT projects' argv are unchanged (ADR-214 route D). Reason: no old program has to refuse a new file; 2.1.0 files open unchanged.

ADR-222 (2.2.0 BUILT) project format 13 (REQ-322, REQ-323, REQ-029). Context: format 12 (2.1.0, committed and pushed, not released) stores `clip_order` as a list of rows (`lut`, `subtitles`, `text:<id>`, `picture:<id>`) and has no text maximum. The new data are the order of every row of a clip (Crop, Change aspect, Scale, Move, Fade, Volume, Clean audio as rows) and the text maximum. Options: (a) optional fields in format 12: a 2.1.0 program would open such a file, drop the unknown row names as damaged (Row::Unknown, repair note) or ignore the maximum, and write it back: the order is lost silently, which breaks the rule that an older program never writes a newer file's content; (b) format 13: 2.1.0 refuses it with its newer-version message and leaves it untouched (REQ-029). Choice (b), decided by the architect: SCHEMA_VERSION 13, loads 1..=13, always written as 13 by 2.2.0; 2.1.0 and older refuse 13. Migration 12 -> 13 in memory: the 2.1.0 `clip_order` entries keep their meaning (see ADR-223), `TextItem.max_size` absent = none. Files saved by 2.1.0 open unchanged. Rejected: writing 12 when the content has no new data (two writers of one format; a copy that loses data when resaved by 2.1.0 is the same risk for the projects that use the new features). Consequence: 2.1.0 is not released, so only the developer builds of 2.1.0 meet the refusal; the release notes say the format changed. Supersedes ADR-221.

ADR-223 (2.2.0 BUILT with a deviation: new rows keep their default place, not the top of the group, for the picture and the sound group) order of all rows per clip. Context: 2.1.0 orders the movable rows (LUT, texts, pictures, subtitles) and builds the fixed rows (Crop, Scale, Move, Change aspect, Fade, Volume, Clean audio, Speed) in a fixed order. Choice: a clip's stored order holds the full order of its two groups (picture group: Crop, Change aspect, Apply LUT, texts, pictures, subtitle lines, Fade IN/OUT, Scale, Move as the business lists them; sound group: Volume, Clean audio); Speed is fixed first and never stored; the stored list is written only when the clip's order differs from the default (as 2.1.0's `to_store`), so the default is the empty list. New rows (a LUT, a text, a picture item, a Crop, a Volume or any other effect added to a clip) go to the top of their group; copies of whole-video effects go to the top of their group on each clip (REQ-321); a row moves only inside its group. Expansion of 2.1.0 stored orders (format 12): the 2.1.0 movable rows are placed above the default sequence of the other rows, so the look of a 2.1.0 project with a changed order does not change: the 2.1.0 build is the default sequence with the stored movable rows on top, in their stored order. Expansion is pure (order_chain.rs) and tested with the 2.1.0 fixtures. Rejected: a per-row numeric position (two rows can never be given the same place by a user drag; the list is simpler and what the widget shows). Row names in the file: `crop`, `frame`, `scale`, `move`, `fade`, `volume`, `clean`, plus the 2.1.0 names `lut`, `subtitles`, `text:<id>`, `picture:<id>`; unknown names are Row::Unknown and repaired with the line "A damaged effect order was repaired" (REQ-311).

ADR-224 (2.2.0 BUILT: three builds; render/steps.rs on an RGBA layer; text as a black and white matte) render steps for a free order (render/steps.rs). Context: the default order must reproduce the 2.1.0 argv exactly (golden tests unchanged); other orders need the picture and sound chains built from the stored order. Choice: a clip whose order is the default keeps the 2.1.0 legacy path (no change in argv); a clip with another order is built step by step from its order (the generalised 2.1.0 overlay stage): the picture layer is an RGBA stream of the source at its current size; Crop crops the layer's content (percent of its current size, even pixels: one formulation at any position); Change aspect (`frame`) fits the layer into the project frame and composes the background under it; Scale resizes the layer's content about its centre (ADR-096 pivot); Move translates the layer inside the frame (overlay offset); Fade IN/OUT is a black alpha ramp on the composed stream (above Frame it fades the background, below Frame it fades the layer only); Apply LUT grades the stream it sits on (above Frame: the whole frame; below Frame: the layer's colours, alpha kept: lut3d on gbrap or a split with alpha re-attached, spike S0e); texts, picture items and subtitle lines are the 2.1.0 overlay steps (ASS and overlay). Pairs and their formulation: Crop/Frame and Crop/Scale: the same percent-based crop expression; Scale/Move: Move is an offset in the frame, Scale about the picture centre, so Move-then-Scale and Scale-then-Move differ and both need the RGBA layer; LUT/Frame and LUT/Fade as above (LUT under the fade stays black only if it maps black to black: stated to the user in the widget tooltip only if spike S0e shows it); texts/pictures/subtitles keep their 2.1.0 overlay form. Golden: default orders unchanged (GATE); each swap has a real-ffmpeg test that the output differs where the business says and matches between preview and export. Alternatives: rebuild every clip with the step builder (changes the argv of every project: rejected by REQ-131/golden gates); a fixed group order with only the LUT movable (rejected by REQ-320).

ADR-225 (2.2.0 BUILT, REQ-320, Andrea's sound rule) sound group chain. Choice: the sound chain of a clip is the 2.1.0 chain with Volume and Clean audio as steps in the order of the sound group (default: Clean audio then Volume, as 2.1.0's `clean before volume`); the dry branch of the Clean audio mix (strength) takes its input at the same point in the chain as the filter, so a swap keeps the mix correct (spike S0e checks the swapped output). Audio fades (fade in and out of the sound) stay fixed after the sound group (derived from REQ-320: the business makes the Fade IN/OUT row a picture row; its sound fade keeps today's place; [TECHNICAL], to confirm in the PE checkpoint). Music is not an effect row and keeps its chain. Speed is applied first to both chains (tempo for sound, setpts for picture).

ADR-226 (2.2.0 BUILT; the 180 px minimum wins at 1280 x 800, about 20%) Applied effects column. Choice: the Preview section is split inside itself: the picture and its controls on the left, the Applied effects column on the right, full section height; column width = max(180 px, share x section width) with the share default 15%, stored as an additive settings field in the saved layout (`applied_share`, permille, default 150, range 80..300; settings version stays 2, ADR-044/195); a vertical border between picture and column is a splitter with the same rules as the section borders (ui/layout.rs `drag`, minimums); the picture shrinks first (REQ-068); the controls row sits under the picture only; popups are not placed in the column. Rejected: a column inside the timeline section (the business puts it in the Preview section); a fixed pixel width (does not follow the window).

ADR-227 (2.2.0 BUILT: only the cap changed) text size model. Context: the 2.0.3 best fit (measure.rs `fit`, text/layout.rs `layout`) already sizes a text to its box in width and height with a cap of 10% of the picture height (MAX_FIT). Choice: the same fit, cap = the text's maximum (ADR-228) or the default 100 permille; the block (wrapped at the box width, measured in glyph widths) is centred in the box on both axes; the ratio is not stored (computed at the current wrap); slide-in keeps its distance from the box (box width or height, so a larger box gives a longer slide, as the built code already does in text/events.rs `slide`); old texts (format 10 and older) keep the 2.0.3 rule with cap 100 permille, so their sizes do not change (REQ-319). Subtitle lines untouched. Rejected: storing the size (a second source of truth that the box would have to keep in step); a ratio stored per text (not needed: the block is measured at the current wrap).

ADR-228 (2.2.0 BUILT, D64) per-text maximum. Choice: `TextItem.max_size: Option<u16>` in permille of the picture height (same unit as the cap, MAX_FIT), serde default None, skipped when absent; valid range 20..=500 permille (2 to 50%); one decimal in the field is 1 permille; the field refuses other values with the business message and keeps the stored value; one undo step per change; an empty field clears it. Layout: `layout` takes the maximum as `max` (min unchanged). Rejected: a second size field (the box must govern the size).

ADR-229 (2.2.0 BUILT: order_chain.rs, pure) pure order model and tests: src/order_chain.rs holds the groups, the default sequences, the expansion of 2.1.0 orders, resolve, move inside a group, drag rules; no render, app or ui import.
